# ADR-0001 - Stage 2 Security Gateway: architecture, toolchain, and dependency policy

**Status:** Accepted (Bundle M complete; M1-M7 decided here)
**Date:** 2026-11-14
**Deciders:** Owner (NSI admins) selected Rust on 2026-11-14; agent drafted and is accountable for the record.
**Scope:** Stage 2 gateway only. Stage 1 (mod_rewrite + responder + controller) is deployed on lab-web01; Stage 3 (containerised Apache) is governed by `docs/CONTAINERIZED-APACHE-HANDOFF.md`.
**Source brief:** `docs/SECURITY-GATEWAY-HANDOFF.md` (owner's platform brief).

Every statement below is marked **[measured]** (verified on a named host in this session),
**[verified]** (confirmed against an upstream source), or **[projected]** (a design judgement
that a later bundle must prove). The brief's own rule - no unfalsifiable mitigation claims -
applies to this document as much as to the policies it governs.

---

## Why this exists (context)

The platform KPI is **time-to-mitigate**: advisory published -> mitigation live on all
protected hosts. Not detection accuracy. That single metric is why the dependency pipeline
(N) and policy-as-data (S) are early work rather than late polish: a mitigation that takes a
week to build and distribute is a week of exposure on every host that has no vendor patch.

The gateway is not a fix for CVE-2026-119618. That CVE is the *test case** for a platform
whose purpose is the next advisory, on a component that has no patch yet.

## Decision 1 (M1) - Components, trust boundaries, and known limits

### Components

| # | Component | Responsibility | Existing or new |
|---|---|---|---|
| 1 | **Gateway listener** | Terminate TLS + HTTP/2 inbound; emit HTTP/1.1 upstream; apply policy before the backend sees the request | new (`gateway/`) |
| 2 | **Policy engine** | Load declarative policy files, evaluate a request against them, return a verdict (serve / tarpit / reject / pass) | new, but consumes the *existing* signature vocabulary |
| 3 | **Quarantine client** | Read the controller's rendered `tarpit-ips.map`; write confirmed claims into the controller spool | new client, existing contract |
| 4 | **Deception client** | Serve the cheap inline drip; delegate stateful deception to the responder | new (hybrid, per owner decision) |
| 5 | **Artifact pipeline** | Build, version, hash, and publish gateway binaries | new (Bundle N) |
| 6 | **Controller** | Lease state, verdict promotion, map rendering | existing, unchanged role |

### Trust boundaries

| ID | Boundary | What is trusted | Failure mode if the trust is wrong |
|---|---|---|---|
| B1 | Internet -> gateway | Nothing. Bytes only; no client identity is inferred from a header the client controls | IP spoofing makes the wrong address quarantined |
| B2 | Gateway -> Apache backend | The gateway's socket address. Apache must accept a forwarded client address **only** from that address | Any client can forge `X-Tarpit-Client` and poison the responder's audit trail (PT-10 class of bug) |
| B3 | Gateway -> controller state | The spool directory, append-only. The gateway is never granted SQLite write access | A compromised gateway could quarantine arbitrary addresses; mitigated by 0600 spool + schema validation + allowlist |
| B4 | Build host -> deployment target | The artifact, by sha256 and recorded provenance | Silent substitution of a binary on a host |
| B5 | Config distribution -> host | Policy files, by version and hash | Two hosts enforcing different policies under one "profile" |

### Expected limitations (stated up front, not discovered later)

1. **The gateway cannot protect itself from a vulnerability in its own stack.** See Decision 4.
2. **HTTP/1.1 upstream removes multiplexing.** One h2 stream set becomes N h1 connections.
   The backend connection count - not CPU - becomes the constraint, and Stage 1's measured
   **[measured]** worker costs (normal request 1.0 ms, tarpit drip 5.26 s, over-quota local
   reject 0.001 s on lab-web01) become the sizing input for Bundle O.
3. **TLS termination moves private-key custody to the gateway**, which changes what a host
   compromise exposes and forces the key-delivery decision in Decision 7.
4. **Apache's HTTP/2 is not automatically out of the picture.** On lab-web01 the `:80` vhost
   advertises `Protocols h2c http/1.1` **[measured]** and `:443` has h2 available. Until the
   backend listener is pinned to `Protocols http/1.1` (task O1), "Apache's HTTP/2 path was not
   exercised" is unfalsifiable no matter what the gateway does.
5. **Response fidelity.** The responder exists to answer like the real server. A Rust gateway
   that answers with a different `Server:` banner or TLS fingerprint hands a scanner a new
   signal. Fidelity work is Bundle T, not a post-deploy apology.

## Decision 2 (M2) - Technology record

**Language: Rust.** (Owner decision 2026-11-14 08:18; alternatives Go / C / nginx+modules /
haproxy recorded in the brief and rejected for programmability and h2-frame access.)

### Toolchain pin

| Host | OS | glibc | rust available | installed now |
|---|---|---|---|---|
| lab-web01.lab | Oracle Linux 8 | **2.28** **[measured]** | `rust-1.92.0-1.module+el8.10.0+90888+4ecfbbd1` (ol8_appstream) **[measured]** | none **[measured]** |
| build01.lab | Oracle Linux 9 | **2.34** **[measured]** | `rust-1.92.0-2.el9_8` (ol9_appstream) **[measured]** | none **[measured]** |

**Decision: pin the toolchain to `rustc`/`cargo` 1.92.0 from the distro appstream module**, not
`rustup`. Rationale: (a) 1.92.0 is the *same compiler version* on both EL8 and EL9, which
removes build-host drift between the two OS generations the fleet runs; (b) a distro module is
vendor-patched and auditable, whereas a `curl | rustup` install on a server is an untracked
supply chain; (c) it is the compiler the target hosts can actually install themselves.
Consequence: toolchain upgrades happen only when both EL8 and EL9 ship the same version
(Decision 6).

### Crate pins (queried 2026-11-14 from the sparse registry `index.crates.io`)

| Crate | Pinned version | Note |
|---|---|---|
| `tokio` | **1.54.1** | runtime; `features = ["rt-multi-thread", "net", "time", "signal"]` |
| `hyper` | **1.12.0** | server + client; HTTP/2 comes via hyper's `http2` feature |
| `hyper-util` | **0.1.21** | required for a hyper 1.x server (`TokioIo`); added to the pins after the first build, which could not link without it |
| `http-body-util` | **0.1.5** | required for request/response bodies; must keep its default features on, or `BodyExt::collect` is unavailable |
| `h2` | **0.4.20** | transitive through hyper; pinned explicitly so Bundle Q can use it directly |
| `rustls` | **0.23.46** | `0.24.0-dev.3` exists and is a prerelease - not used |
| `ring` | **0.17.14** | **selected crypto provider** (see below) |
| `aws-lc-rs` | 1.19.0 | available alternative, **not selected** |

`Cargo.lock` is committed and is the source of truth; the table above is the pin *policy*, the
lockfile is the pin *fact*. **[projected]** exact resolution is confirmed at first build (N5).

**Registry access note [measured]:** from build01, `https://crates.io/api/v1/...` returns
**HTTP 403** while `https://index.crates.io/...` works. `cargo` uses the sparse index, so
builds are unaffected, but any tooling that scrapes the crates.io web API will need a proxy or
an exception. Recorded so a future "cargo works but the audit tool doesn't" is not a mystery.

### Crypto provider: `ring`, and the native-code truth

The brief's instruction was explicit: *do not assume rustls eliminates native cryptographic
code.* It does not.

- `ring` compiles **C and x86-64 assembly** as part of the build.
- `aws-lc-rs` compiles **C and assembly** from the AWS-LC source tree, and additionally requires
  a working C toolchain and cmake-class tooling on the build host.
- A pure-Rust provider is the only option that removes native code entirely; it is not the
  default and it is not what `rustls` pulls in by default.

**Decision: `ring`.** Reasons: it is the long-standing default provider exercised by hyper and
rustls documentation and CI; `aws-lc-rs` adds a larger native build surface (cmake, a bigger C
tree) on a host whose C toolchain we would then have to keep patched as its own supply chain.
**Consequence recorded honestly:** choosing Rust does not remove the C compiler from the
supply chain, and the gateway's attack surface includes compiled C either way.

**Fallback [projected]:** if `ring` fails to build against glibc 2.28, the order of resort is
(1) `podman build FROM oraclelinux:8` on build01 (N1), (2) `aws-lc-rs`, (3) musl static
(N4, documented as fallback only).

## Decision 3 (M3) - Repository integration (no parallel classification system)

New paths in `~/projects/Fleet-Filter`:

```
gateway/                     Rust crate (Cargo.toml, Cargo.lock, src/)
  src/listener/              TLS + h2 accept, h1 upstream client
  src/policy/                policy loader and evaluator
  src/spool/                 claim writer (same schema the responder already writes)
  src/backend/               routing table: name -> upstream backend
gateway/policies/*.toml      policy-as-data (Bundle S), one file per policy
data/artifacts/              versioned artifact records (sha256, provenance)
```

Changes to existing code:

- **`controller/signatures/signatures.yaml` becomes the single classification vocabulary.** The
  same signature record feeds `bin/render-signature-rules.py` (Apache rules, shipped in L1) and
  `gateway/policies/*.toml`. A gateway policy references a signature id; it does not re-declare
  a regex.
- **`controller/adaptive-tarpit.py`** keeps sole authority over leases. The gateway reads the
  rendered map and writes claims to the spool - the contract already implemented and tested for
  the responder (`drain-spool`, commit `7ebaa8a`). No new API is added before one is needed.
- **`apache/*.conf`** are unchanged in Profile B apart from backend routing and `Protocols`
  (task O1).
- **`systemd/`** gains `fleet-filter-gateway.service`; existing units are untouched.

Explicitly forbidden, because it is how this project would silently fork in two:
a second regex store, a second verdict vocabulary, a second lease database, or a gateway-local
policy that exists only in code.

## Decision 4 (M4) - Threat model

| Attack surface | Threat | Mitigation in the design | Residual risk |
|---|---|---|---|
| **Apache (httpd/mod_http2)** | Vulnerability in the backend's HTTP/2 parser (the CVE class this project started on) | Gateway terminates h2; backend pinned to `Protocols http/1.1` (O1) so the h2 parser is not reachable on that listener | Apache's HTTP/1.1 parsing is still exposed; a vuln in core httpd request handling is not mitigated by the gateway |
| **The gateway's own stack** | **Zero-day in rustls, hyper, h2, tokio, or ring** | Small feature surface (no templating, no docroot serving, no dynamic modules), pinned dependencies, systemd unit hardening, per-IP connection caps, and a one-command fail-open: stop the gateway and Profile B degrades to Profile A with the existing vhost serving directly | **No mitigation exists before the vendor patch.** This is the accepted cost of the platform and the reason the feature set stays deliberately small |
| **The tarpit** | Worker exhaustion from held drip connections | Quota + over-quota state 2 (measured 0.001 s local reject vs 5.26 s held drip **[measured]**), proven to clear in H7 | A flood that exceeds the quota converts to mass 503s, which is itself observable to the attacker |
| **Spoofed client identity** | Client forges `X-Forwarded-For` / `X-Tarpit-Client` so the wrong address is quarantined or logged | B2: Apache accepts forwarded addresses only from the gateway's address; the responder already refuses untrusted header values (`tests/security/test_input_hardening.py`, 93 checks **[measured]**) | Until `mod_remoteip` is configured with the gateway as the only trusted proxy, header-based identity remains advisory |
| **Control-plane compromise** | An attacker who can write `state.db` or the spool can quarantine any address, including an admin | Spool is append-only with 0600 mode and a dedicated owner; controller validates schema and quarantines malformed claims to `failed/`; allowlist protects designated addresses | The controller runs as root; a compromised controller is not contained by these controls |
| **Resource exhaustion at the gateway** | Connection flood / slowloris against the new listener | fd limits, per-IP connection caps, read and write timeouts, bounded worker pool | Memory and fd headroom on lab-web01 have not been measured for the gateway process; required before O-bundle |
| **Policy bypass** | Request shaping (case variation, duplicate headers, whitespace, h2 pseudo-header tricks) evades a signature | The gateway evaluates *parsed* structures rather than raw strings, so normalisation is possible where mod_rewrite cannot | Signature coverage is variant-based; an unmodelled encoding evades until a policy exists |

## Decision 5 (M5) - Inspection capability matrix

Every policy must state its claim category **and** name (i) the vulnerable operation, (ii) the
route by which a matched request would have reached it, and (iii) the evidence artifact that
demonstrates variant coverage. A policy that cannot produce (iii) may not claim more than
**detection only**.

| Policy | Claim category | Vulnerable operation | Route to that operation | Variant-coverage evidence |
|---|---|---|---|---|
| `h2-in-h1-out` (the milestone itself) | **Demonstrated isolation** - *once O3 completes* | mod_http2 HTTP/2 frame/header parsing on the backend | h2 connection to the backend listener | O3 must capture: backend `Protocols`, connection count on the backend's h2 listener, and Apache access-log proof that the request arrived as HTTP/1.1. Until then the claim is **projected**, not demonstrated |
| `h2c-preface-on-http1-listener` | **Detection only** | none reachable | Apache answers a raw h2c preface with 400 **before** mod_rewrite runs **[measured, lab-web01 and build01]** | measured log fixtures in `signatures.yaml` |
| `CVE-2026-119618:probe_path` | **Demonstrated targeted mitigation** | `assign_headers()` in mod_http2 | only via an h2 request that reaches the vulnerable module | positive/negative fixtures in `signatures.yaml` + `tests/unit/test_signatures.py` (29 checks **[measured]**); caveat: matching a PoC string is evidence of *that variant*, not of the class |
| `CVE-2026-119618:bodyless_ct`, `connect_ct`, `filler_headers`, `authority_localhost` | **Detection only** for the variants the gateway cannot observe inline; **targeted mitigation** where the gateway can evaluate the parsed header set | same | same | per-variant fixtures; `render-signature-rules.py` records which variants are renderable vs log-only **[measured]** |
| behavioural scanner detection (Wazuh / Fail2ban) | **Detection only** | n/a | n/a | Wazuh rule set pending owner approval (`docs/WAZUH-ASK.md`) |
| future Apache CVE with no policy yet | **Detection only** | n/a | n/a | none until a policy file exists |

**Rule adopted:** "targeted mitigation" is a claim about a *route*, not about a string. A policy
that cannot name the route it closes is downgraded to detection-only automatically.

## Decision 6 (M6) - Dependency security policy

| Item | Policy |
|---|---|
| Advisory monitoring | `cargo audit` (RUSTSEC) runs as a build step. A vulnerable or unmaintained advisory **fails the build** unless a waiver is recorded in `gateway/audit-waivers.toml` with an owner, a reason, and an expiry date. |
| Crate version policy | Exact versions via committed `Cargo.lock`. No floating requirements in the lockfile. Toolchain pinned to the distro module (1.92.0); the toolchain moves only when EL8 and EL9 ship the same version. |
| Rebuild cadence | Weekly dependency rebuild **[projected]**, plus an immediate rebuild on any RUSTSEC advisory touching a locked crate. This is the mechanism Bundle S distributes through (N6). |
| Emergency deploy path | Copy a published artifact + `systemctl restart fleet-filter-gateway`. **No compilation on the target** during an incident. Rollback is a symlink/version swap, not a rebuild. |
| Artifact retention | Keep the current plus two previous versions, each with sha256, git commit, toolchain version, and lockfile hash recorded in `data/artifacts/`. |
| Vendoring | Build-time fetch from the sparse index with checksum verification. Vendoring crates into the repo is the fallback if registry access from the build host becomes unreliable (note the 403 on the crates.io web API, Decision 2). |

## Decision 7 (M7) - Service identity separation

| Aspect | Decision | Basis |
|---|---|---|
| Accounts | Gateway runs as a dedicated `fleet-filter-gw` system account. The controller runs as root (existing units). The responder runs as `nobody` (existing). No two components share an account. | A compromised network-facing listener must not inherit write access to controller state |
| TLS key delivery on EL8 | **0600 key file owned by the gateway account.** `LoadCredential=` is unavailable: measured `systemd 239 (239-82.0.13.el8_10.19)` reports `Unknown lvalue 'LoadCredential'` **[measured]**; the feature landed in systemd 247 | The brief required the measured result, not the upstream feature list |
| TLS key delivery on EL9 | `LoadCredential=` is supported (systemd 252) **[verified]**, **but the 0600 file is used on both OS generations** so one unit file serves the fleet and profile drift cannot come from an init-system difference | Composability contract item 1 |
| Spool permissions | The gateway writes its own spool subdirectory; the controller reads it. The responder's existing spool (`/var/lib/adaptive-tarpit/spool`, `nobody`-owned **[measured]**) is not shared with the gateway | Prevents one writer's file mode or SELinux context from breaking another's |
| Apache's view | Apache must not be able to read the gateway's private key | Key custody boundary (B2/B3) |
| SELinux | Toolbox01 is permissive **[measured]**; the gateway unit ships its own context requirements rather than relying on the host mode | A permissive host today is not a guarantee for the fleet |

## Consequences

**Positive**
- One classification vocabulary (signatures.yaml) now feeds both enforcement layers, so a new
  advisory is one data change plus a rebuild, not a code change in two places.
- The isolation claim for the milestone is *provable* (O3) instead of asserted.
- Toolchain and crate versions are pinned to facts that were checked on both OS generations.
- The unavoidable self-protection gap is written down rather than argued about later.

**Negative / costs accepted**
- Rust keeps a C toolchain in the supply chain via `ring` (or a larger one via `aws-lc-rs`).
- HTTP/1.1 upstream costs connections; capacity work is required before the gateway can front a
  busy host.
- Two more artifacts (binary + policy set) now need distribution, versioning, and rollback
  machinery that Stage 1 alone did not need.
- Pinning to the distro module means the compiler only advances as fast as Oracle ships it.
